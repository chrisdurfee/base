# Base 4.0 — bundle architecture, tree-shaking and cacheability

Shipping as `4.0.0`. Phases 0 through 2 (`3.9.8`) fixed leaks and correctness
and `3.9.9` fixed the cache performance regression those phases introduced.
This phase changes no algorithm. It changes what ends up in a consumer's
bundle and how much of it survives a rebuild.

Phase 0's numbers stay in `phase-0-baseline.md`. The size comparison point
throughout is the tree as it stood at `ba065b0`, immediately before this work.

## Verification status

| gate | result |
| --- | --- |
| `npm run test:run` | 78 passed / 78, 14 files |
| `npm run build` | clean, `tsc` included |
| `npm run size` | no entry regressed past 3% except the three noted below |
| `npm run cache:check` | core chunk survives every feature edit |
| consumer tree-shaking | verified against Vite 7 / Rollup, not asserted |

## The headline

The `component` subpath used to be *larger* than the whole root bundle, which
made code splitting pointless: an app that imported only the UI toolkit
downloaded more than an app that imported everything.

| entry | before gzip | after gzip | change |
| --- | --- | --- | --- |
| root | 30,526 | 31,017 | +1.6% |
| ajax | 3,720 | 4,197 | +12.8% |
| html | 7,172 | 7,755 | +8.1% |
| date | 2,049 | 2,274 | +11.0% |
| data | 16,355 | 16,839 | +3.0% |
| state | 16,940 | 9,550 | **−43.6%** |
| component | 30,998 | 21,927 | **−29.3%** |
| router | 30,485 | 27,395 | **−10.1%** |

`component` is now 9,090 gzip bytes *under* the root bundle instead of 472
bytes over it. `state` nearly halved.

### The total went up, and that is the trade

Deduplicated across shared chunks, the whole `dist` tree went from 14 files /
64,376 gzip to 19 files / 68,146 gzip, up 5.9%. Finer chunk granularity costs
import boilerplate and gives the minifier fewer modules to overlap.

This is the intended trade and it is only a good one because nobody downloads
all 19 files. The number that matters is what a single consumer pays, and for
the three largest entries that number fell substantially. If a future change
makes the aggregate matter more than the per-entry figures, this decision is
the one to revisit.

### What a real bundler actually drops

Per-entry figures still assume the consumer wants the whole entry. Measured
through Vite 7 in library mode against the packed tarball, importing one
symbol:

| consumer imports | before raw | after raw | change |
| --- | --- | --- | --- |
| `Data` from `/data` | 60,142 | 44,974 | −25.2% |
| `SimpleData` from `/data` | 60,180 | 37,322 | −38.0% |
| `Model` from `/data` | 60,140 | 60,341 | +0.3% |

`Model` costing marginally more is correct: it is the one case where the model
service is genuinely reachable.

## Breaking changes

### 1. Directive registration is explicit

`default-directives.js` no longer registers anything when imported. It exports
a function.

```js
// before - registration happened as an import side effect
import '@base-framework/base/dist/modules/layout/directives/core/default-directives.js';

// after
import { registerDefaultDirectives } from '@base-framework/base';
registerDefaultDirectives();
```

**Importing from the package root is unaffected.** `src/base.js` calls
`registerDefaultDirectives()` itself, so every built-in directive is present
on import exactly as in 3.x. This only matters if you were relying on the bare
side-effect import directly.

Directives are now grouped into three tables you can register selectively:

```js
import { registerDirectives, coreDirectives, reactiveDirectives } from '@base-framework/base/component';
import { routerDirectives } from '@base-framework/base/router';

registerDirectives(coreDirectives, reactiveDirectives, routerDirectives);
```

Registering the same name twice replaces the earlier handler, which is how you
override a built-in.

The `component` subpath registers `coreDirectives` and `reactiveDirectives`.
The `router` subpath registers `routerDirectives`. This is what lets an app
that never routes avoid paying for `route` and `switch`.

### 2. `route` and `switch` no longer import the router singleton

They resolve it through a registry at call time. `src/modules/router/router.js`
registers itself when imported.

If you use the `route` or `switch` directives you must import the router
somewhere — either `@base-framework/base` or `@base-framework/base/router`. If
you do not, the directives log an error and no-op rather than silently
rendering nothing.

This is what breaks the chain that pulled the entire router into any bundle
touching the directive table.

### 3. `Model` no longer imports `Ajax`

`ModelService` sends through an injected handler:

```js
import { setModelRequestHandler } from '@base-framework/base/data';
```

Importing `@base-framework/base` or `@base-framework/base/ajax` registers the
default XHR transport automatically, so both of those paths behave as before.

**If you import `Model` from `@base-framework/base/data` and never import the
ajax module, model requests now throw `No model request handler.`** Either add
the ajax import or register your own handler. In exchange, importing `Data`
from `/data` no longer drags the XHR stack in.

### 4. `Model.prototype.service` is an accessor

It moved from a `Model.prototype.service = ModelService` assignment below the
class body to a getter/setter pair inside it. A top-level property mutation is
a side effect no bundler can prove is safe to drop, and it pinned
`ModelService` — and the entire `Model` class with it — into every bundle that
imported anything from the data entry. That single statement was worth 15kb
raw on a `Data`-only consumer bundle and 22kb on a `SimpleData`-only one.

Reads and plain assignments behave as before; `tests/regression/model-service.test.js`
pins the four access paths. The only visible difference is that `Model.extend`
now uses `Object.defineProperty` internally.

### 5. `for` row scoping is opt-in

`data.scope()` allocates a `Data` instance and two link subscriptions per row
per render. Most row callbacks never touch the third argument.

```js
// before - scoped by default, opt out with false
['items', (item, i, scoped) => ...]

// after - not scoped by default, opt in with true
['items', (item, i, scoped) => ..., true]
```

If your row callback uses the third argument, add `true`. If it does not,
delete nothing and get the allocation back.

### 6. `base.buildLayout()` is root-only

The `base.augment` call moved out of `builder.js` into `base-layout-methods.js`
and is invoked by `src/base.js`. Rendering a layout no longer drags the `base`
singleton into the code-split bundles.

`base.buildLayout()` still exists when importing from the package root. It is
not present if you only import `@base-framework/base/component`; use
`Builder.render` there.

### 7. `sideEffects` is narrowed

```json
"sideEffects": ["./dist/base.js", "./dist/modules/ajax.js", "./dist/modules/component.js", "./dist/modules/router.js"]
```

Those four register something on import. Everything else is now declared pure.

**This was measured and it buys nothing on its own.** Blanket, narrowed and
`"sideEffects": false` produce byte-identical output across all six consumer
scenarios. esbuild pre-bundles each subpath into a single file, so per-file
side-effect marking has almost no granularity to act on; what actually decides
tree-shaking is statement-level purity *inside* those files, which is what
changes 2, 3 and 4 above address.

The narrowing is kept because it is now accurate and costs nothing, not
because it produced the wins.

### 8. Build target names the floor browsers

`target: ['safari14.1', 'chrome84', 'firefox79']`, replacing `es2020`, which
in turn replaced `esnext`.

**The support floor moves from iOS Safari 14.0 to 14.1** (April 2021). That is
the only breaking part of this change.

The es-year labels turned out to be a poor way to say what we meant. Asking
esbuild for `es2020` is not the same as asking it for Safari 14 / Chrome 80 /
Firefox 74 — naming those browsers explicitly costs **271 more** gzip bytes
than `es2020` does, so `es2020` was emitting syntax that floor does not fully
cover. Naming browsers keeps the stated floor and the emitted syntax from
drifting apart.

The entire cost of the old target was one lowered feature. esbuild lowers
class fields into a `__publicField` helper, emitted as its own 223-byte chunk
that **all seven subpaths import**, so it cost each of them an extra HTTP
request as well as bytes. Probing esbuild's `supported` flags one at a time,
the helper disappears only when both `class-field` and `class-static-field`
are available. Public instance fields shipped in Safari 14.0; public *static*
fields shipped in 14.1. There are no private class fields anywhere in `src`,
so `class-private-field` is irrelevant.

Measured, combining this change with the sourcemap change below:

| entry | before | after | delta |
| --- | --- | --- | --- |
| root | 31,017 | 31,018 | +1 |
| ajax | 4,197 | 3,816 | −381 |
| html | 7,755 | 7,409 | −346 |
| date | 2,274 | 2,019 | −255 (−11.2%) |
| data | 16,839 | 16,301 | −538 |
| state | 9,550 | 9,140 | −410 |
| component | 21,927 | 21,434 | −493 |
| router | 27,395 | 26,865 | −530 |
| distinct outputs | 68,146 | 67,333 | **−813** |

Distinct live output files drop from 19 to 18 — that file, and the request
it cost every subpath, is the `__publicField` chunk. `date` returns to 2,019,
below its pre-4.0 number, so the regression noted in the headline table is
resolved.

`es2022` and `esnext` remain byte-for-byte identical to each other, meaning
nothing in `src` uses post-ES2022 syntax. The earlier note that "`es2022`
needs Safari 15.4" is true of the *label* but not of this codebase's actual
syntax, which is why naming browsers gets almost the whole win at a floor of
14.1 rather than 15.4.

A `browserslist` key would not help: esbuild reads only `target`, so a
`browserslist` entry would be documentation that silently disagrees with the
build.

### 9. Sourcemaps are external

`sourcemap: 'external'`, replacing `sourcemap: true`.

Not breaking; it fixes a bug. The `files` whitelist excludes
`dist/**/*.map`, but `sourcemap: true` still appended a `sourceMappingURL`
comment to every emitted file. Every published file therefore pointed at a
map that was not in the tarball, producing a 404 in every consumer's
devtools. `'external'` still writes the maps to disk for local debugging but
omits the comment, and the emitted JS is otherwise unchanged.

## Non-breaking build changes

- `dist` is removed and recreated on every build, so a renamed or deleted
  entry can no longer leave a stale file behind.
- `metafile` is written to `dist/meta.json` for graph analysis and excluded
  from the published package via `files`.
- `define: { __DEV__: 'false' }` and `drop: ['debugger']`.
- `prepublishOnly` runs the full `npm run build` (esbuild **and** `tsc`)
  rather than esbuild alone, so declarations can no longer go out stale.

## Cacheability

`npm run cache:check` (`scripts/chunk-stability.js`) asserts that the core
runtime chunk sits at the bottom of the graph and does not rehash when
unrelated features change.

The core chunk holds six modules — `types.js`, `strings.js`, `tracker.js`,
`tracker-types.js`, `data-tracker.js`, `events.js` — imports nothing but
esbuild's runtime helper chunk, and keeps its hash across a synthetic edit to
each of six feature probes spanning ajax, component, date, html, router and
state. The check applies the edit through an esbuild `onLoad` plugin, so it
never writes to disk and is safe to run in CI.

An explicit `src/entries/core.js` entry point was tried first and abandoned:
it fragmented the graph and made every entry larger. Asserting the boundary
as an invariant gets the same guarantee without the bytes.

## Where `lru-cache.js` landed

`src/shared/lru-cache.js` became a shared module in 3.9.9, so it was worth
checking that it did not get duplicated or drag anything.

It is a leaf — it imports nothing. Four modules import it, spread across four
different chunks (`watcher-helper.js`, `basic-data.js`, `data-utils.js`,
`import-wrapper.js`), and esbuild still emits exactly **one** copy, 620 bytes
in `chunk-KRDITJSA.js`, because the other three chunks already import that
chunk. No duplication and nothing dragged.

Its placement in the data-core chunk rather than the core runtime chunk is
correct: its four importers are reachable only from the `data`, `state`,
`component` and `router` entries, which is precisely that chunk's entry set.
Promoting it to the core chunk would ship it to `ajax` and `html` consumers
who never touch it. Editing it does not rehash the core chunk.

## `mangleProps`: assessed and rejected

Measured with `mangleProps: /^_/` across the 57 underscore-prefixed internal
property names:

| | plain | mangled | change |
| --- | --- | --- | --- |
| all outputs raw | 201,539 | 198,895 | −1.31% |
| all outputs gzip | 68,146 | 67,683 | **−0.68%** |
| `dist/base.js` gzip | 31,017 | 30,796 | −0.71% |

Not enabled. 0.68% gzip does not pay for:

- `dist/types/*.d.ts` is emitted by `tsc` from source and would keep declaring
  `_init`, `_retainState` and the rest after they stop existing at runtime.
- Subclassing is first-class API here (`Model.extend`, `Component`, `Jot`,
  `Pod`, `Data`). A consumer subclass overriding or calling any `_` member
  would break with no diagnostic.
- `Object.assign(ExtendedModel.prototype, settings)` never mangles
  user-supplied keys, so a setting meant to override an internal would quietly
  stop connecting.

The one hazard that would have made it an outright bug is absent: the only
underscore string literal in `src` is `'_blank'`, an anchor target, not a
property access. If the trade is ever revisited, a trailing-underscore
convention applied only to genuinely private members would be the safe form.

## Not done

- The root bundle still pulls the router, so `import { DateTime } from
  '@base-framework/base'` costs 117kb raw in a real consumer bundle against
  8kb from `/date`. The root is a single self-contained side-effectful file by
  design; the subpaths are the answer, and this is worth saying louder in the
  README than it currently is.
- `ajax` (+226) and `html` (+334) remain above their pre-4.0 gzip even at
  `es2022`. Both are chunk-boundary redistribution rather than new code, but
  neither was chased down.
